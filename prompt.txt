**Issue 1 — Alert rate-limiting (Medium severity, runtime correctness)**

In `alerting.py`, the `send_attack_alert_async()` method is called once per classified ATTACK flow with no rate-limiting. Under a real PortScan or DoS flood, the system can classify hundreds of ATTACK flows per minute, spawning a new daemon thread for each one and making an SMTP or HTTP connection for each. This floods the operator's inbox/Telegram and can exhaust system resources.

Fix: Add a per-channel cooldown to `_dispatch()` inside `AlertManager`. The minimum interval between dispatches for the same subject prefix (e.g. same attack type) should be configurable via an env var `ALERT_COOLDOWN_SECONDS` defaulting to 60. If a dispatch is suppressed by the cooldown, log it to stdout but do not fire the external channel. Track the last-dispatch timestamp per channel key in the existing `_channel_state` dict. No new dependencies — use `time.time()` for comparison.

**Issue 2 — `FLOW_ACTIVITY_TIMEOUT` default in `.env.example` (Medium severity, accuracy)**

`.env.example` ships with `FLOW_ACTIVITY_TIMEOUT=10`. The models were trained on CIC-IDS2017 flows using CICFlowMeter's default of 120 seconds. Setting timeout to 10 seconds causes flows to expire far earlier than the training distribution expected, distorting time-based features like `Flow Duration`, `Flow IAT Mean`, `Active Mean`, and `Idle Mean`. This silently degrades model accuracy for any slow or long-lived connection without any warning to the user.

Fix: Change the default in `.env.example` to `FLOW_ACTIVITY_TIMEOUT=120`. Add a commented-out line below it showing the demo shortcut: `# FLOW_ACTIVITY_TIMEOUT=30  # lower for faster demo feedback, reduces fidelity`. Also add a startup warning in `live_ids.py`: if `FLOW_ACTIVITY_TIMEOUT` is less than 30, print a clearly visible warning like `[Config] WARNING: FLOW_ACTIVITY_TIMEOUT={value}s is very low. Features may not match training distribution (trained at 120s). Consider raising this value.`
